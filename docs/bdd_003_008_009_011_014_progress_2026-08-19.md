## Incidencia adicional — `NotificationManager cancel` repetitivo

Causa raíz:

1. El store reescribía y reprogramaba recordatorios sin distinguir un reemplazo idéntico.
2. La inicialización restauraba alarmas antes de conocer la proyección autenticada.
3. Había 342 propietarios heredados `agenda:dose-*`, uno por ocurrencia de medicamento.
4. Lifecycle y sync podían iniciar reconciliaciones simultáneas.

Corrección:

- Reemplazos idénticos son no-op nativo y conservan el ID estable.
- Inicialización configura el plugin, pero difiere la restauración hasta conocer sesión/bebé.
- Orden: calcular deseados → podar obsoletos → restaurar faltantes → aplicar proyección.
- Reconciliación serializada entre lifecycle y sync.
- Namespace heredado `agenda:dose-*` se elimina aunque el snapshot antiguo lo marque retenido.
- Limpieza grande usa una sola operación de cancelación masiva y después recrea sólo alarmas vigentes.

Evidencia:

- Notification policy: 19 tests PASS, incluidos no-op idéntico, bulk idempotente, limpieza forzada de `agenda:dose-*` e inicialización diferida.
- Notification coordinator: 8 tests PASS, incluido el orden de poda y la exclusión de dosis históricas.
- APK profile final: build PASS.
- Instalación limpia, ventana estable de 20 s: 0 cancelaciones.
- Siguiente arranque frío, 20 s: 0 cancelaciones.

Durante la validación del snapshot heredado, `adb install -r` devolvió `Success` pero Android dejó el paquete sin registrar y fue necesario reinstalar. Esto eliminó el snapshot local usado para la medición; por esa razón no se declara una segunda medición física sobre esos mismos 342 propietarios. La regresión exacta queda cubierta en el store y coordinador, y la instalación final quedó sin churn.
